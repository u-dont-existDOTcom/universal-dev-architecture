## Credential boundary

The owner manually creates `/etc/mission-control/capability-nonce-publisher/github-token` on PRIMARY, with directory root:root 0700 and file root:root 0600. The file contains only the dedicated fine-grained PAT (one trailing newline permitted). It must be scoped only to `u-dont-existDOTcom/universal-dev-architecture`, Issues read/write, with no other selected permissions. Never put its value in a command argument, shell history, chat, issue, repository, environment variable, or log. Populate using a trusted interactive protected-file editor; do not paste the token into a shell command.

The publisher service uses systemd `LoadCredential` to expose a private read-only copy to its isolated non-root identity. The environment variable **name** is `MISSION_CONTROL_CAPABILITY_GITHUB_TOKEN_FILE`; the unit sets its **path value** to `%d/github-token` (systemd's per-service credentials directory). The PAT value is never an environment variable. Do not mount the credential into Mission Control or the relay.

On the verified PRIMARY systemd runtime this private copy is root:root 0440 in a root:root 0550 service directory, with service-private ACL access. Do not chmod/chown that copy or grant the app's `joel` group access. The runner accepts this only at `/run/credentials/mission-control-capability-nonce-publisher.service/github-token`, with matching `CREDENTIALS_DIRECTORY`, trusted non-writable ancestors, an exact read-only tmpfs/ramfs mount, and pinned inode/device/owner/group/mode checks. PID1's private credential setup is the trust boundary; tmpfs alone is not a non-swappability claim. A network-denied, nonsecret fixture test verified the actual service copy without opening a PAT.

GitHub's fine-grained PAT is repository/permission-scoped, not issue/create-only scoped. The isolated broker is the mandatory narrower boundary: its only remote mutation is creation of `MISSION_CONTROL_CAPABILITY_NONCE_V1` comments on exactly issue #60. The local API cannot choose repository, issue, comment body, URL, token, update/delete action, decision receipt or stage receipt. Reads are bounded exact-bus publication reconciliation. No generic GitHub mutation endpoint exists.

## Recovery and rollback

An ambiguous publication retains its candidate in PUBLISHING; restart finds and verifies an existing exact comment before activation and never blindly re-POSTs. If publication cannot be proved, the gate stays closed. Expired unpublished candidates remain immutable historical rows; one new pending candidate can replace them. Rotation never carries forward capability PASS.

Use the retained old app container/image and exact private runtime configuration to roll back app deployment; keep the same database volume and preserve new immutable history. Stop/disable the new publisher service if reverting this feature. Restore only the backed-up changed relay source files, never the entire relay package over the lock repair. Do not delete nonce comments, old challenges, queue state, registrations, or credentials. A rollback does not make stale capability receipts current.

Live acceptance is incomplete until the owner-provisioned credential is installed and actual publication and canonical capability receipt evidence pass.
