# Canonical Design OS bootstrap

## Rule

When a task materially involves UI, UX, frontend visual implementation, website or application design/redesign, long-form reading experience, visual hierarchy, typography, color, layout, motion, interaction design, component design, design systems, design study/critique, accessibility/responsive visual review, or design-production auditing, recover and use the current `u-dont-existDOTcom/design` repository before substantive design work.

Start with the live default-branch `skills/design/SKILL.md`, then follow its task-relevant read order. Do not reconstruct the design methodology from remembered chat context, stale adapters, or generic model taste.

## Authority

This is a specialist dependency, not a replacement for project authority. Apply this precedence:

1. current owner instructions and project-specific product/content truth;
2. verified current project state and constraints;
3. current universal development architecture;
4. current `u-dont-existDOTcom/design` specialist guidance for design-domain decisions;
5. generic framework conventions, catalog suggestions, anti-pattern heuristics, and agent taste.

Where the design repository itself defines a stricter local authority order, follow it within the design domain so long as it does not conflict with higher project or owner authority.

## Retrieval and freshness

- Resolve the live `design` default branch at task start.
- Read `skills/design/SKILL.md`; load only the additional core/reference/project files relevant to the task.
- If the consuming project has a profile under `design/projects/`, use it as specialist project context but reconcile it against the consuming project's live repository before relying on it.
- Treat remembered copies and generated adapters as caches only. The live design repository wins on freshness.
- If `u-dont-existDOTcom/design` is unavailable, do not invent its current rules. Continue only from current local/project requirements and record the missing specialist dependency.

## Activation boundary

Use this dependency when design quality or visual/interaction behavior can materially affect the result. Do not load it for backend-only, data-only, infrastructure-only, or prose-only work with no design surface.

For non-interactive artifacts such as reports, diagrams, or presentations, reuse the design repository's applicable hierarchy, perception, typography, anti-slop, and verification modules while leaving medium-specific production rules to the relevant artifact workflow.

## Required behavioral consequences

Using the design repository means, at minimum:

- preserve supplied arguments, claims, and product truth rather than editing them to fit a layout;
- diagnose lower-layer perceptual failures before downstream styling;
- distinguish refinement from redesign;
- treat catalogs and anti-pattern lists as evidence/heuristics rather than absolute authority;
- verify accessibility, responsiveness, applicable interaction states, performance, and consistency where relevant;
- use bounded visual verification rather than indefinite polishing;
- persist reusable design decisions and lessons in the appropriate repository rather than leaving them only in chat.

## Why this is universal

Design work recurs across unrelated projects, while a generic coding agent otherwise tends to rediscover or inconsistently apply design workflow, accessibility checks, anti-slop rules, project-context conventions, and source provenance. A single specialist repository gives all projects one recoverable design architecture without copying its full contents into every project.
