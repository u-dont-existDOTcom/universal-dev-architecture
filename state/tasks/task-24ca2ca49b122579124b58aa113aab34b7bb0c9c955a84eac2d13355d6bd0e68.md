- Evidence on that baseline:
  - A registered task can't be enrolled in the fleet watch: enrollment accepts only task ids its records carry, and a registered task has none.
  - Once watched, its open waiting record is classified as an owner action, so the check would notify the owner instead of asking a supervisor.
  - Routing a question needs a durable decision boundary (a receipt, directive, queue and the like), and a registered task has none of those either.
  - The native Work dispatcher runs every worker's native-Work directive; nothing limits it to one task.

## Completed

- **`lib/fleet-supervisor.ts`.**
  - New trigger `FIRST_SUPERVISION_REQUIRED`: a registered task waiting for its supervisor routes reasoning and doesn't notify the owner. It is checked before the owner-action rule, and only for the registration's waiting reason.
  - A registered task's decision boundary falls back to its registered contract, so the first question can be asked. Other workers keep the old rule.
  - The first question's requested decision: the first bounded step within the owner's allowed scope and must-never limits, native ChatGPT Work only for collection Chat can't do reliably and only where the allowed scope includes it, and no spending, publishing or weakening of the contract.
  - The question goes to the existing project-manager chat (Extra High), as every fleet question does; no new supervisor chat is needed.
- **`lib/fleet-watch-enrollment.ts`.** A registered worker can be enrolled under `task:<worker>`; an unregistered worker still can't use an id its records don't carry.
- **`lib/jev-shadow-telemetry.ts`.** The shadow comparison expects `route_reasoning` for the new trigger and doesn't expect an owner decision for it.
- **`lib/chatgpt-work-cloud-autodispatch.ts`, `scripts/run-chatgpt-work-cloud-autodispatcher.ts`.** The dispatcher requires `MISSION_CONTROL_CHATGPT_WORK_AUTODISPATCH_WORKERS_JSON`, a non-empty JSON array of worker ids, and dispatches only for those workers. Without a valid list it refuses to start.
