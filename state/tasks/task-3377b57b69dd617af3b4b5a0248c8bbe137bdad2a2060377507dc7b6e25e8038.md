# Current State — Mission Control: the owner may retry a native Work start that failed at the ChatGPT app

## Goal

- Task ID: `pr-419`.
- Branch: `claude/mc-work-start-retry-20261022`.
- On 2026-10-22 the Atlas task's supervisor authorized a new Work job (open until 2026-10-24), and the dispatcher's start of it ended `UNAVAILABLE` (`WORK_CLOUD_PRODUCT_TOOL_EXECUTION_UNAVAILABLE`) (#385). The owner's read-only checks found the cause: the dispatcher's executor thread belonged to an earlier ChatGPT app, and Mission Control's own app refused every request from it. That was repaired on the server the same day. But the failed start is ambiguous by design, so nothing starts the job again: the dispatcher never re-creates under a recorded result, and the expiry question never counts such a job as unrun. This lets the owner authorize one retry, guarded by a read-only search for a Work thread of the failed start.

- Round 2, after the hosted checks, Codex's review and an independent review of `e508a5f9`:
  - A failed start must settle before its retry (Codex P1, "Do not launch after a single negative thread scan"): the owner's authorization is accepted only 30 minutes or more after Mission Control recorded the failed result, and the store refuses an authorization whose time isn't its own receipt time (within 5 minutes). The controller checks the 30 minutes again before the search, so a create call that lost its answer has had time to complete and its thread to show in the listing.
  - Only an `UNAVAILABLE` start, or one that `FAILED` with `WORK_CLOUD_APP_EXECUTOR_FAILED`, is retried: a wrong surface or a mismatched or ambiguous thread can mean a thread holding the prompt exists outside what the search reads. Each start's latest result counts (a start that waited for setup and then failed is failed).
  - The search no longer narrows by project, allows 10 minutes of clock skew, and says NONE only when the listing has a thread list that reaches back before the failed start (any page without an older thread, an empty or unparseable listing, is INCOMPLETE).
  - The retry's private request carries the failed start's request time, result time and prompt digest in every state, so it never changes once recorded; before its request is recorded it may be rewritten (a held retry comes back with a new time). A failed start whose prompt doesn't rebuild to its digest is read from its own private request file, only if it matches the digest. A retry already recorded isn't searched again.
  - The chain starts at the failed start the ledger's authorization names; a repeated owner action counts only the current directive's authorization; the worker page summarizes the new record (the typecheck failure on `e508a5f9`).
- Round 3, after an independent review of `b72e68bd` (hosted checks green there):

Only an older ChatGPT (or unknown-kind) thread shows that the listing reaches back.
  - A start that made a thread (it waited for setup) is never retried, whatever its latest result.
