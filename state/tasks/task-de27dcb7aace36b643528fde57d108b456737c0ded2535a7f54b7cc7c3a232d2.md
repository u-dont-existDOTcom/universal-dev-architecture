# Mission Control owner dashboard: what each task's supervisor is doing, an honest supervisor button, and a first screen that shows what needs the owner

- Branch: `claude/mc-honest-supervisor-link-20261010`.
- Task ID: `pr-356`.

## Goal

- The owner can reach a worker's supervisor chat from the dashboard, or sees plainly that none is linked; the button never opens the ChatGPT home page or a demo address.
- The first screen shows what needs the owner's decision first, then the alarms Mission Control raised itself in plain words with the task's supervisor at hand, then the tasks; project and watch internals sit in the details.
- The owner can see what each task's supervisor is doing: what it was last asked, whether that went out, the answer, and the ChatGPT chat where it ran; and whether supervisor chats can be reached at all.

## Authority / baseline

- Owner: on 2026-10-10 the owner reported that the dashboard's supervisor chat button only opens chatgpt.com, so the dashboard was unusable for reaching supervisors, and on 2026-10-11, after the deploy of main, that the dashboard is still not useful: its "Your decisions and actions" listed Mission Control's own alarms (missing owner-action telemetry, an overdue non-owner step) as if they were owner decisions. Merges after a clean review and green checks are approved; the owner's hand is on each merge. On 2026-10-11 the owner held the deploy until the dashboard is usable: "the point is i need to be able to see what the supervisor chat is doing. if there's no supervisor chat then it has to make one, and they need to roll over with handoffs after a while as well."
- Baseline: main at `af8d2983`.

## Completed

- `lib/projection.ts`: no `https://chatgpt.com/` fallback; a worker without a recorded route or link gets an empty supervisor address and `supervisorChatIsPlaceholder: true`, so the runtime status counts it as missing.
- `components/SupervisorLink.tsx`: recorded real link first, else the owner-configured specialist chat for the worker from `/api/supervisor-directory` (read once per page), else "No supervisor chat linked" with a link to the supervision page; demo addresses are not offered as links.
- Worker detail passes the worker id; styles for the not-linked state.
- Review repair: the live dashboard's "Current tasks" card (`OwnerTaskCard`) now shows the same supervisor control. `HealthyCard`, changed first, is not rendered by the live dashboard.
- Second and third review rounds: `lib/supervisor-chat-address.ts` decides whether an address opens one specific chat: an HTTPS ChatGPT conversation address (`/c/<id>`, optionally inside a project `/g/<project>/c/<id>`, the same ids the configured chats accept), not a demo or placeholder; the home page, settings or sign-in pages and other sites don't count. Both projections and the button use it, also for configured chats; a projection picks the first recorded address that passes (the route's, then a supervisor chat link set later), so an invalid route address never hides a valid link (fourth review round). The configured-chat directory is read once at a time, a good answer is reused for a minute and a failed read is never remembered; each button looks again after a minute (15 seconds after a failure), so it recovers and shows a chat configured later without a reload.
- Tests: an unlinked worker renders the not-linked state with no ChatGPT home link; a real recorded chat stays a link; a demo address is not offered; the "Current tasks" card shows the control for recorded, missing and demo addresses; a recorded ChatGPT home page, settings page or other site is not offered; directory failures are retried, a good answer is reused, and the button looks again after a minute; the first screen tells decisions from Mission Control's alarms and words an overdue step plainly; a link set later wins over an invalid route address; every made-up owner action is classified; the card's "Your action" for alarms, decisions and none; the button's checking, unavailable, none and link states and their order; a read that never answers, carries malformed entries or reports an invalid list counts as failed and never replaces a good answer. A late reader refreshes at the shared answer's expiry; a last answer is kept through failures for five minutes, not indefinitely.

- First screen (`components/Dashboard.tsx`, `lib/owner-view.ts`): `ownerAttention` separates real owner decisions and actions from the alarms the projection raises by itself (reason codes `OWNER.ACTION_TELEMETRY_MISSING`, `OWNER.ACTION_TELEMETRY_LEGACY`, `OWNER.NONE_NEXT_ACTION_OVERDUE`, `OWNER.NONE_NEXT_ACTOR_NOT_CURRENT`, `OWNER.ACTIVE_DIRECTIVE_CONFLICT`, `OWNER.DIRECTIVE_DELIVERY_FAILED_NO_RETRY`); `OWNER.CORRECTION_BLOCKED_BY_OWNER` stays the owner's, and a test fails if the projection makes up a code that has no place. The projection's fail-closed state is unchanged; the owner view shows "Needs your decision" (real ones only), then "Needs a look" (each alarm in plain words with the task's supervisor control), then "Current tasks", then the queue; "Projects and supervision" moved into the details. Task cards say "Waiting for your decision" or "Needs a look: …". A shorter coverage line keeps the not-everything-reports caveat. Checked in a local run of the app with demo data.
- Fifth review round: a task card's "Your action" comes from the same split (`ownerActionForCard`): the owner's own action in its recorded words, or for an alarm "Nothing to decide." with the plain explanation, never the alarm's internal text. The supervisor button tells a directory it can't read yet from one that has no chat for the worker: "Checking for a supervisor chat…" until the first answer, "Couldn't check for a supervisor chat; trying again" after an error status, a network failure, a malformed answer or ten seconds without one, and "No supervisor chat linked" only once the directory says so (or there is no worker to look up). A failed read keeps the last answer for the same worker; an answer for another worker is never used.
- Sixth review round: only a list the server reports as configured or as not configured is an answer. A list it reports as invalid comes back with no entries; that is now a failed read ("Couldn't check…"), not "No supervisor chat linked", and it never replaces a good cached answer.
- Seventh review round: a button that read the shared answer late looks again when that answer expires (at least a second later), not a full minute after its own read, so every button refreshes together; a failed read keeps a button's last answer for five minutes at most, then it says it couldn't check.

- Supervisor activity (after the owner's 2026-10-11 request): `lib/supervisor-activity.ts` derives, per task, every question Mission Control queued for a supervisor chat (route messages V1-V6), its state (waiting to be sent, sent, finished, answered, sent but unanswered, expired unsent, withdrawn, replaced), the relay's send and finish times and the ChatGPT conversation it ran in (only from verified collector evidence, only an address that names one conversation, the real address preferred over a provisional "WEB:" one), and the answer's gist (the decision's reasoning summary, or the question it puts to the owner). Every projected task carries `supervisorActivity` (newest five, totals). Task cards get a "Supervisor" line; the worker page gets "What its supervisor is doing" with each question, its state, times, answer and "Open this chat"; the supervisor button opens the task's latest supervisor chat first. The first screen says whether supervisor chats can be reached (the relay to ChatGPT is up) and when the last question went to ChatGPT, or that they can't be reached (relay degraded or unavailable, per host), or that routine checks have no Project Manager supervisor to ask; it does not claim supervision runs, which the daemon's fleet check decides. The supervision page now reads V5/V6 questions, shows each question's real state instead of the frozen "queued for provider relay", stops showing "waiting for supervisor" once a question is answered or expired, and shows each task's latest question and chat. A closed (not open) owner action no longer reads "Waiting for your action".
- Review of the supervisor view: the first screen says supervisor chats can be reached only when the relay is up and the Project Manager supervisor is itself reachable (otherwise "isn't proven reachable yet"); an operator status without well-formed supervisors (or with malformed host freshness or last-send fields) is not accepted as a refresh, so the last-known view stays; the button keeps the newest chat that was reached even when the five newest questions never got one (`latestConversationUrl` over all questions).
- Second review of the supervisor view: a route message counts as a question only if its packet passes the structural checks (version, packet kind, queued delivery state, this worker, a destination, a queue time and, for provider-session cycles, a later expiry) and, in the projection, Mission Control's own cycle-request parser (`parseCycleRequest`, now exported); a request the fleet check retired because it expired reads "never sent; it expired", and only other retirements read "withdrawn".
- Each question opens a fresh ChatGPT chat with a write-up of the task's state (the relay's design), so a missing chat is made per question and the hand-off happens every time; a standing per-task chat is created only by a manual relay command, and the turn-3 rollover rule is validated but never produced. Recorded as the owner's question on the owner page; this change only makes the activity visible.
