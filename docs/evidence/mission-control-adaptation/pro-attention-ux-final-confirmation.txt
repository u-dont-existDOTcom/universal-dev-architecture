2. Remaining schema-blocking loopholes
Blocker A — Free-form finding-status transitions could bypass the correction lifecycle

The packet says:

findings start as immutable OPEN records;

finding_status_changed events derive MITIGATED, RESOLVED, INVALIDATED, or REOPENED;

CORRECTION_RESOLVED requires every bound finding to be RESOLVED or INVALIDATED.

That is insufficient unless the store also validates how a finding reached RESOLVED or INVALIDATED.

Otherwise, an emitter could append:

finding_status_changed:
  OPEN → RESOLVED

without a current CORRECTION_VERIFIED event, thereby satisfying the aggregate resolution gate while bypassing all evidence requirements.

Require every status-change event to carry at least:

finding_id
from_status
to_status
reason_code
basis_event_ids
actor_id
actor_role
occurred_at
candidate_digest
contract_hash
owner_outcome_hash

Enforce these transition rules:

RESOLVED

Must reference a current, valid CORRECTION_VERIFIED event whose:

finding binding includes this exact finding;

candidate digest matches;

contract hash matches;

owner-outcome hash and epoch match;

evidence-requirement schema matches;

verification policy remains current;

verification receipt has not been invalidated or reopened.

An explicitly authorized non-correction resolution pathway may exist, but it must have an equally strong evidence basis and a distinct reason code. A bare status assertion is invalid.

INVALIDATED

Must reference:

the evidence showing the original finding was unsupported, obsolete, duplicated, or malformed;

an authorized invalidator identity and method;

an invalidation reason code;

any affected directive withdrawal or supersession event.

Invalidation must not project as successful correction.

MITIGATED

Must include:

mitigation evidence;

residual risk;

remaining required response;

next review trigger.

REOPENED

Must reference the exact durable event or binding change that invalidated prior closure.

This is a validation/schema invariant, not merely a UI concern.

Blocker B — Verification invalidation triggers remain incomplete

The packet explicitly implements reopening when the current:

candidate changes;

contract changes;

owner outcome changes.

The first-turn freshness requirement was broader. A previously valid verification can also become invalid when any of the following changes:

verification_policy_hash
evidence_requirement_schema_hash
assignment_epoch
target_epoch
relevant execution environment
source snapshot or source corpus
verifier method version, where policy declares it material

For example, a scientific verification performed under an obsolete AskRigor evidence schema must not remain VERIFIED merely because the report digest did not change.

The robust schema is to make validity dimensions explicit on each verification:

verification_validity_scope:
  candidate_digest
  contract_hash
  owner_outcome_hash
  verification_policy_hash
  evidence_requirement_schema_hash
  assignment_epoch
  target_epoch
  environment_bindings
  source_snapshot_bindings
  invalidate_on

Any change to a declared validity dimension must:

make verified = false;

make resolved = false;

project CORRECTION_REOPENED;

identify the exact invalidating event;

append a durable reopen event or an equivalent causally linked invalidation record.

A projection-only reopen with no durable causal reference would weaken auditability.

Closure-label safeguard

CORRECTION_RESOLVED should also carry a closure basis:

CORRECTED_AND_VERIFIED
FINDING_INVALIDATED
MIXED_RESOLUTION

This prevents an all-invalidated finding set from appearing as though corrective work succeeded. The lifecycle may be closed, but the operator-facing label should be:

CLOSED — FINDING INVALIDATED

not:

CORRECTION COMPLETED

This can be incorporated into Blocker A rather than added as a separate lifecycle state.

Reasonable follow-on hardening, not schema blockers

These improvements are worthwhile but do not prevent freezing after the two invariants above:

Publish a machine-readable transition matrix and property-test illegal transitions.

Add an explicit CORRECTION_PROGRESS_RECORDED or lease-renewal event for long-running corrections. Until then, lease expiry correctly fails closed, so this risks false negatives rather than false claims of progress.

Validate authorized-executor and verifier roles against a durable authorization-policy version rather than trusting a role string.

Test duplicate delivery receipts, replayed acknowledgements, out-of-order events, clock skew, and concurrent predecessor conflicts.

Add historical replay tests proving that the same event stream always produces the same projection.

Show the closure basis and reopening trigger prominently in the detailed audit view.
