# State and Recovery Agent Instructions

These instructions apply to current-state checkpoints, handoff files, lesson ledgers, and recovery records in this directory.

- State files are concise routing documents, not chat transcripts or substitutes for exact repository evidence.
- Before trusting or editing a checkpoint, inspect actual Git state, relevant commits, current artifacts, and newer owner instructions. Repair stale entries immediately.
- Record goal, authority/baseline, active owner constraints, completed work not to repeat, current step, last verified durable boundary, remaining work, blockers/uncertainty, evidence/tests/commits, and next safe action.
- Update state at meaningful durable boundaries, after consequential decisions or falsified approaches, before handoff, and before claiming multi-step work complete.
- Never store credentials, secret values, private chain-of-thought, unnecessary personal data, or large raw logs here. Link to canonical evidence.
- Clearly separate `verified`, `observed`, `unverified`, `blocked`, and `planned`; do not convert plans or remembered summaries into completion claims.
- A state checkpoint never outranks current owner instruction, exact repository state, canonical protocols, tests, or source evidence.
- Transferable findings still require semantic lesson disposition and provenance. A current-state file is not a lesson index.
- After interruption, context compaction, model switch, or a fresh thread, identify exactly what survived and resume from the latest verified durable boundary without repeating completed work.
