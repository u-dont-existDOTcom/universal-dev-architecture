# Authoritative minimal workflow

1. **Interpret and continue.** Read the owner request and applicable repository instructions. Extract acceptance criteria, constraints, and authority. Proceed through routine safe work on reversible assumptions; ask only for a material tradeoff, missing authority, consequential action, or ambiguity that would change the outcome, and explain options plus a recommendation when asking.
2. **Inspect first.** Read the relevant code, tests, Git state, and exact project commands. Reproduce a defect or establish a characterization baseline before changing behavior.
3. **Plan proportionally.** Use no plan artifact for a trivial change, a short in-turn plan for moderate work, and one repository execution plan plus recovery checkpoint for substantial multi-step work. Never maintain competing ledgers.
4. **Choose isolation and ownership.** Default to one agent for small or tightly coupled work. Use one task branch/worktree for substantive work and parent-local subagents only for demonstrably independent surfaces; keep one integrating parent and serialize shared mutable state. Coordinator is not part of the minimal stack; if deliberately reevaluated for substantial recovery-sensitive work, keep it disabled by default. Its active shared-checkout board additionally requires an explicit marker, exact task identifiers, and two or three durable verticals. Never create a second coordination graph or progress ledger.
5. **Implement the smallest complete slice.** Prefer a failing regression test when practical, make the narrow production change, and keep public APIs and unrelated behavior stable.
6. **Diagnose failures systematically.** Gather evidence, form and test hypotheses, fix the root cause, and avoid speculative patching. Preserve useful existing work.
7. **Verify once, well.** Run focused checks, then the exact repository-wide checks proportionate to risk. Inspect the final diff and Git status. Completion claims require fresh captured evidence; correct work that never reaches terminal handoff is not end-to-end success.
8. **Add specialized review only when triggered.** Use one independent native code review for material risk. The Codex Security formal pipeline is optional and empirically uncertain; use it only when explicit formal security work needs canonical artifacts. If selected, its worker orchestration becomes the sole coordination system for that phase and must terminate within a stated budget.
9. **Persist the durable boundary.** Update the one repository plan/state file at meaningful boundaries, commit intentionally, and use the PR as the long-lived review/handoff link. Do not create generic handoff files.
10. **Integrate under existing authority.** A reversible local merge may proceed under the standing global agreement after checks and rollback preparation. Push, PR publication, external tickets, releases, deployments, or configuration mutations require their existing explicit authority.

For long-running commands, start them in a native PTY/session, poll the same process until terminal, preserve logs/status, and resume from repository state after interruption. Do not release the task merely because the command is still running. Prefer complete, robust work over shortcuts taken only to save time, but do not expand into tangential or unnecessary work.
