## Working diagnosis

The local history supports a failure pattern: a justified constraint was treated as proving a particular unrequested implementation, then local reviews optimized that implementation. The proposed additional emphasis is not merely preserving the promised outcome. It is checking whether an assistant-created method has quietly become a mandatory prerequisite for reaching that outcome.

Example: reproducible, theory-blind comparison does not by itself establish that every participant must complete a comprehensive externally coded taxonomy. A stable representation and a closed taxonomy are different choices. Preserving a promise to deliver a useful interview eventually would not expose this detour if all intervening work were labeled a necessary dependency.

Other possible contributors requiring evidence include stale handoffs, poor lesson activation, reviews with overly narrow scope, and failure to route plain Chat work through an applicable control. Do not claim a particular implementation defect or model mechanism without checking the execution path.

## Minimal candidate adaptation

### 1. Separate requirements from method hypotheses

Before a consequential method commitment, keep one compact section in existing task state: owner outcome; genuine constraints and their sources; proposed method and its origin; most important assumption; strongest materially simpler alternative; smallest decision-changing example; authorized scope and next evidence boundary.

An assistant hypothesis must not acquire owner authority through repetition, file naming, a hash, a green test, or a downstream worker contract. Approval of a bounded action does not approve undisclosed methodological consequences. A fixed experimental version preserves reproducibility, not eternal correctness.

Ask specifically: what breaks if this prerequisite is removed or replaced? A source showing that a method is useful is not proof that it is necessary. Research should examine the underlying problem and competing approaches, rather than only literature inside the chosen paradigm.

No need to document every minor implementation choice. The trigger is a material shift in the promised result, who makes judgments, evidence semantics, owner/user workload, costly dependency, or long-lived architecture.

### 2. Test an ordinary case before scaling the abstraction

Show a small end-to-end specimen early: realistic input, actual proposed interaction/output, and the decision it serves. Distinguish a conceptual walkthrough from an executed test. Use a representative case and a difficult counterexample rather than a curated success alone.

When a rule blocks an ordinary supported fact, compare at least these possibilities: legitimate uncertainty about that precise claim; wrong subtype/model of the fact; unsuitable higher-level strategy. Do not assume the remedy is explanatory wording or another schema field.

Repeated owner difficulty with the same underlying problem should reopen the premise before another local repair. One severe counterexample can be sufficient; a fixed failure count is not a universal scientific threshold. Pause the affected expansion, not unrelated safe work.

### 3. Separate premise review from implementation review

A consequential strategic review should start with the independently recovered owner request, corrections, delegated authority, constraints, and one concrete output. The reviewer forms an initial account of what the task actually needs before reading the builder's rationale. Then compare the current plan with the simplest plausible alternative.

Technical review asks whether the implementation meets its specification. Premise review asks whether that specification and method deserve to govern this task. Both can matter; one cannot substitute for the other. A reviewer scoped to record containment should not be blamed for failing to redesign the product, but that narrow PASS must never be promoted into product validation.

Use the existing reasoning-supervision lane; do not add a second permanent committee. Fresh-context review is warranted at material conceptual forks or repeated premise failures, not every commit. Different model branding or repeated approval is not proof of independent or correct judgment.

### 4. Make supervision legible and consequential

At meaningful checkpoints, show the owner: what they will actually get; the important assumption introduced by the assistant; what has changed since the last agreed example; direct evidence of improvement or lack of it; the next bounded action; whether a substantive owner decision is needed.

The owner-facing view should normally fit on one screen. Supporting test results and exact hashes remain available but must not dominate the explanation of progress. If the next decision cannot be explained in ordinary language, the handoff is not ready for informed approval.

Routine in-scope reversible work continues without approval. Escalate consequential changes in product meaning, decision authority, evidence interpretation, substantial user burden, or other nondelegated tradeoffs. On ambiguity, prefer the cheapest safe reversible probe; do not silently harden an unapproved approach.

Mechanically, current owner-source versions, explicitly delegated authority, scope, stale approvals, and invalidated directions can be checked at action boundaries. Whether an inference is justified is a semantic judgment; a machine checking that a field says MATCH has not verified that judgment. A Chat path outside a runtime gate must not be advertised as gate-protected.

## Owner supervision support

The system should supply these prompts rather than require constant vigilance:

- What will the user experience on one ordinary case?
- Which consequential requirement did the assistant infer rather than receive?
- What is the simplest alternative, and what evidence rules it out?

A useful owner's early correction is: the broad goal is right, but this method or burden is not what I intend. The owner need not supply a complete technical replacement. The assistant should first represent the objection faithfully, then determine whether it concerns wording, implementation, semantics, or strategy.

Maintain evidence-grounded disagreement. Do not replace loyalty to the old method with automatic agreement with every new owner objection. The owner controls goals and tradeoffs; factual and scientific claims still require appropriate evidence. Participant endorsement of a pattern is not by itself external behavioral validation.

AI assistance can prepare compact decision comparisons and perform premise checks during active work. Unattended cross-project monitoring requires an explicitly configured execution/supervision path. This proposal creates none.

## Pilot before promotion

Use the existing policies as the baseline, not no supervision. First inspect one actual decision path from the source incident to locate the missed activation, interpretation, scope, or enforcement boundary.

Then replay a small set of decision prefixes, without giving the reviewer the later critique as an answer key. Compare current policy behavior with an explicitly activated compact premise check. Add unrelated tasks and harmless routine changes. The source incident is development data, not an untouched generalization test.

Include cases where the owner outcome remains verbatim intact but an unjustified prerequisite has been added; where all technical tests pass on the wrong method; where an owner explicitly delegates the method; where repeated local repairs fail; and where the simpler path really violates a hard safety or scientific constraint. The expected result is not always less structure or more owner approval.

Evaluate: detection before consequential commitment, specificity and correctness of the objection, preservation of useful work, owner decision time, unnecessary interruptions, work spent before detection, and resulting owner-facing quality. Set a small evaluation budget and acceptance criteria before running. A favorable report or schema-valid receipt is not the success measure.

If the baseline fails because an existing rule was not connected to the actual workflow, fix that connection first. Amend existing patterns/templates only for demonstrated gaps; do not append another global checklist by default. Broad adoption needs evidence beyond a replay of this known case.
